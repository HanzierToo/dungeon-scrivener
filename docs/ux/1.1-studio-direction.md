# Studio 1.1: interface and first-run tour

This is the design direction for the authoring Studio. It builds on the 1.0 contracts and leaves the player runtime and archive formats alone.

## The working idea

DungeonScrivener should feel like a writing desk attached to a map. The dark ink header identifies the project. Warm paper surfaces hold the work. Copper marks primary actions and the current place. The typography gives stories room to breathe, while controls remain compact enough for a working editor. The interface uses system fonts and local assets so the Studio remains useful offline.

The primary path is **start a project → write a scene → connect it → test it → download the authoring copy → export the game**. The home page explains that path in three short steps. In the workspace, editing modes are separate from play and download actions. Project diagnostics remain visible below the work, and the current project stays in the header.

## Editor layout

- **Sage** is the file desk. It opens `world.json` when available, so the editor has a useful starting point. The file list and code editor have distinct surfaces. File actions remain in the file list, and open files remain visible as tabs.
- **Apprentice** is the story map with an inspector. Selecting a scene exposes its title, story text, and actions. The inspector separates scene editing, world settings, and script declarations. Script source still opens in Sage.
- **Playtest** stays separate from authored files. It shows the isolated debugger. **Play** shows the reader interface.
- **Project ZIP** is the editable backup. **Game ZIP** is the portable reader copy. The two actions stay named distinctly throughout the UI.

The map and inspector are side by side on wider screens and stack on narrow screens. The map stacks scenes vertically on phones so scene labels stay legible. Existing package controls remain keyboard reachable. Visible focus, readable contrast, and reduced-motion settings apply to the shell and the tour.

## First-run tour

After a person creates a project for the first time in this browser, a short dialog offers **Start tour** or **Not now**. Importing an existing project does not prompt. Either dismissal or completion is remembered locally. **Take the tour** in the workspace starts it again at any time.

The six steps spotlight the project identity, Sage file desk, Apprentice map and inspector, Playtest, project ZIP, and game export. The rest of the screen is dimmed and blocked from accidental clicks. Each step explains one task. Back, Next, Finish, Exit, and Escape are available. The card receives keyboard focus and keeps tab navigation inside it while open.

The tour changes between Sage and Apprentice to show the real interface. It does not create content, start a game session, save, or export on the author's behalf. Leaving the tour preserves the current project.

## Acceptance checks

1. A new project offers the tour once. Skipping and finishing both prevent an unsolicited repeat; manual replay works.
2. Every step points to a rendered control or work area, and the tour works at desktop and narrow widths.
3. Apprentice scene edits appear on the map and in `world.json`. World settings and script declarations are reachable from the inspector.
4. Existing create, import, Sage, playtest, play, project download, recovery, and game export flows still work.
5. Run the production build and Studio browser suite on the current checkout. Record any browser-specific failure with the exact command and result.

The 1.0 release evidence already records a WebKit internal error on Studio's offline `page.reload()` check. This remains an open browser gate until a real Safari offline-reload run establishes the product behavior. The other Studio journeys and the exported-game checks should still be run in WebKit.

## Next design work

The 1.1 shell makes existing features findable, but the older package controls still need deeper editing passes. Prioritize scene outline and keyboard map navigation, inline diagnostics linked to an exact field or file, fewer raw-ID inputs in Apprentice, and clearer Sage file actions. Those changes should follow the current model and VFS contracts and receive their own browser checks.
