# DungeonScrivener 1.0 security threat model

Status: Task 4 deliverable. This document is a design and verification checklist, not evidence that the listed controls are implemented or that a sandbox is absolute.

## Scope and security goals

DungeonScrivener imports projects and plays exported games in a user's browser. Project ZIP contents, authored source, save ZIPs, media, and CSS are untrusted, including projects created by the user. The authoring site also renders project content in editor previews. There are no accounts, server-side game state, collaboration features, or required runtime services.

Protect these assets and properties:

- The editor and player document, their browser origin, and other projects' recovery records.
- Integrity of the active project snapshot and game session. A rejected import must not partially replace either.
- Availability of the browser tab and local storage when processing hostile or oversized inputs.
- The offline export promise: declared local game resources may load, while project content does not initiate network or unrelated local-file access.
- Authored file bytes and paths. Security validation must not silently rewrite or discard recoverable project content.

This model covers malicious or malformed project and save input, intentional abuse of the supported authoring features, and accidental unsafe integration. It does not protect a device from a compromised browser or operating system, malicious extensions, developer tools, or a user who deliberately edits and runs an exported game. ZIP player saves are portable data, not signed or tamper-proof credentials. No server-side authorization or anti-cheat boundary exists.

## Trust boundaries and current evidence

The intended flow is:

1. A project or save ZIP enters through a file picker or drag-and-drop and is parsed into a bounded, in-memory virtual file snapshot.
2. Structured documents are validated by the model. Other files remain opaque and inert unless a specific accepted reference assigns them a supported role.
3. Script source is parsed to the documented subset and validated IR. The engine accepts only validated effects and owns state changes.
4. Markdown becomes a safe render AST. Managed media resolves by local asset ID. Player CSS is separately validated and isolated from editor chrome.
5. Recovery records remain browser-local. Player saves are explicit downloads and imports.
6. Export includes only declared playable inputs and the trusted runtime. Its index.html is opened directly from disk and loads referenced local media.

The current contract drafts provide numeric input budgets and package owners in [docs/contracts/budgets.md](../contracts/budgets.md) and [docs/contracts/package-apis.md](../contracts/package-apis.md). They are implementation targets, not runtime proof. [docs/feasibility.md](../feasibility.md) currently says Task 1A is not accepted: automated Chromium and Firefox flows pass, Playwright WebKit fails before the file page loads, and Safari screenshots show only partial manual evidence. Therefore no production isolation or complete three-engine direct-open claim is made here. Recheck that evidence before accepting script execution and export work.

Task 1C fixtures are not present yet. The recipes below use small generated inputs and can later be repeated against accepted fixtures; they do not rely on a fixture ID.

## Prioritized threat table

Priority meaning: P0 blocks release of the affected path until the control is demonstrated; P1 is high risk and must be covered by its owning task; P2 is a bounded risk with an explicit user action or recovery path. Owners refer to the task/package boundaries in the current plan and may be refined by the orchestrator.

| Priority and untrusted input | Attack and impact | Required mitigation and owner | Verification recipe |
| --- | --- | --- | --- |
| **P0: ZIP member paths** (project and save archives) | Traversal names, absolute paths, backslashes, drive or UNC names, control characters, non-NFC aliases, trailing dots, device names, duplicate entries, or case-colliding names can overwrite files, escape an extraction root, or make the validator and consumer select different content. A duplicate project.json can bypass checks. | Do not extract to the host filesystem. Validate every raw member name before adding any member to the snapshot. Reject unsafe names, duplicate/case-collision keys, and collisions with reserved structured paths. Keep accepted spelling and bytes unchanged. Validate before publishing the snapshot. Owner: 10A/10B VFS and ZIP. Apply the same safe archive policy to 27B player saves. | Generate archives containing ../world.json, /world.json, C:/world.json, backslash traversal, NFC/NFD aliases, reserved-name case variants, duplicate project.json, and file/directory collisions. Each is rejected with a path diagnostic; no partial snapshot becomes active and the source ZIP remains available for recovery. Include mixed separators and invalid UTF-8 names. |
| **P0: ZIP expansion and parser exhaustion** (project and save archives) | A compressed bomb, many tiny entries, an oversized member, deeply nested structured JSON, or forged declared sizes can consume memory, CPU, or block the tab. A timeout may leave a partially imported project. | Enforce input bytes, actual streamed expanded bytes per member and total, entry count, path length, JSON size/depth, and time limits before retaining full output. Do not trust ZIP headers or declared sizes. Parse in a cancellable worker where supported; discard partial state on any limit or CRC failure. Use the current budgets draft as the ceiling: 128 MiB project ZIP, 256 MiB expanded total, 64 MiB per file, 20,000 entries, 16 MiB structured JSON, depth 64; player-save ZIP 8 MiB. Owner: 10B VFS and 27B save codec. | Test each exact limit and one byte or entry over it, forged sizes, a high-ratio deflate member, 20,001 empty entries, deep JSON, CRC mismatch, and cancellation. Confirm bounded memory behavior where measurable, a diagnostic, a responsive/cancelable UI, no active-state change, and preserved input. |
| **P1: ZIP format ambiguity** (archive metadata) | Encryption, split volumes, Zip64, symlinks or special files, unsupported compression, malformed headers, or CRC mismatch may be interpreted differently by the ZIP library and downstream code. | Accept only the explicitly supported store and deflate members. Reject unsupported flags, structures, types, inconsistent metadata, and CRC failures. Compare actual bytes to validated limits as they are produced. Keep archive parsing in the VFS/save owner; do not add a second permissive parser. Owner: 10B and 27B. | Build one archive for every rejected feature plus malformed local/central header disagreements. Confirm the same rejection in project and save import, before replacing any snapshot or session. |
| **P0: Arbitrary project files** (any unrecognized path or extension) | A project may contain HTML, JavaScript, SVG, JSON that resembles a script, or a filename crafted to exploit extension or MIME sniffing. Accidentally previewing, importing, linking, or exporting it as executable content can turn inert data into code. | Preserve arbitrary files as opaque bytes. Only exact, validated manifest/world references may activate recognized script, Markdown, CSS, or managed-media handling. Never run a file because of its extension or contents. Export only declared playable files, not the entire project tree. Owner: 10B, 12A, 22B, and 28A. | Import arbitrary HTML, JS, SVG, and misleading mixed-case extensions beside a valid game. Search the exported ZIP and network/resource trace: none is executed, rendered as markup, or included as playable input unless an explicit supported reference permits it. Confirm project ZIP round-trip still preserves the bytes. |
| **P0: Script source and IR** (JavaScript, Lua, Python, imported or generated IR) | A parser gap, source-to-IR mismatch, forged IR, prototype-bearing maps, or an execution shortcut can expose browser globals or let a script alter state outside the engine. Native evaluation of project text can execute arbitrary code. | Parse with the pinned frontends; never eval or run original source. Reject unsupported syntax rather than approximating it. Validate every IR structure at the execution boundary, including imported/generated IR. Execute only the validated IR using the isolation approach accepted by Task 1A; expose immutable reads and narrow typed requests. The engine validates all requests transactionally. Treat opaque-frame messaging as hostile: bind the channel to the expected frame, validate messages, and never treat origin null alone as identity. Owner: 16A/16B, 17A, 18A, 19A, and 13A. | For each source frontend and the IR entry point, attempt DOM/global access, dynamic import, eval, prototype access, constructors, native calls, storage, network, local-file reads, and malformed effect payloads. Confirm compile/IR rejection or capability denial, no host state change, and no unhandled exception in Chromium, Firefox, and WebKit after the isolation route is accepted. |
| **P1: Script parser and execution budgets** (deep or intentionally expensive source) | Deep syntax can overflow parser stacks; huge collections, recursion, an infinite while loop, or many effects/events can freeze the tab or cause partial state changes. | Enforce source bytes before parsing; cap syntax nodes and nesting; execute with shared instruction fuel, loop and call-depth limits, collection/string allocation limits, wall-time supervision where available, and per-action effect/event limits. Abort the enclosing transaction on any breach. A worker timeout must terminate the work rather than merely stop awaiting it. Owner: 16A/16B, 17A, 18A, 19A, and engine transaction owner 13A. | Run inputs exactly at and just over each documented budget, a recursive helper, a non-terminating loop, parser-deep nesting, collection growth, and an event flood. Confirm a bounded diagnostic, tab responsiveness, zero committed partial effects, and successful next action. |
| **P0: Markdown and link rendering** (node text, locale strings, embeds) | HTML injection, event attributes, SVG/MathML payloads, javascript/data/file/blob URLs, protocol-relative links, or malformed link destinations can execute script, navigate to local data, or trigger unsolicited requests. DOM clobbering or unsafe HTML sinks can corrupt the surrounding UI. | Parse to the specified SafeBlock AST, with raw HTML disabled. Build DOM from typed nodes and text, never by assigning authored strings to an HTML sink. Allow only contract-approved https, mailto, and same-document links after parsing and validation. User activation is required for navigation. Sanitize any generated preview markup as defense in depth. Keep source unchanged. Owner: 20A and the player/editor renderers 22A/23A. | Render script tags, event handlers, malformed tags, SVG/MathML, encoded and mixed-case URL schemes, protocol-relative URLs, data URLs, and unsafe link titles in both preview and player. Confirm the source displays as text or receives a diagnostic, no code runs, no automatic request occurs, and an allowed link works only after a click. |
| **P1: Embed expansion** (node links and embeds) | Recursive or highly branching embeds can exhaust CPU/memory or create unexpectedly large output. Ambiguous references can link to unintended content. | Resolve node embeds only by stable ID; detect active-stack cycles and impose the draft limits for depth, expanded nodes, and rendered bytes. Emit bounded placeholders and diagnostics while preserving source. Owner: 20A and 12A. | Test self-embed, two-node cycle, unknown ID, a branching graph beyond each limit, and repeated navigation labels. Confirm termination, bounded output, correct ID resolution, and actionable diagnostics. |
| **P0: Author CSS** (referenced project stylesheet) | CSS can obscure controls, imitate editor chrome, use selectors against host DOM, or request remote/local resources through imports, URLs, fonts, and other loading properties. A parser bypass can affect the editor or exfiltrate data through requests. | Apply styles only inside the isolated player surface, never the authoring chrome. Parse and validate CSS rather than relying on substring filtering; fail closed for unparsed constructs. Block resource-loading constructs and network requests in offline output. Do not permit arbitrary author CSS in the host document. Preserve the original CSS file bytes. Owner: 22A and 28A/28B; isolation follows accepted 1A strategy. | Use selectors that target the app shell, fixed overlays, @import, escaped URL spellings, remote fonts/backgrounds/cursors, and file URLs. Confirm only player content can be styled, no remote or unrelated local resource is requested, controls remain operable, and the CSS file remains byte-preserved in project ZIP round-trip. |
| **P1: Media files** (images, audio, ASCII text) | An active format or polyglot disguised as a supported image/audio file may execute when embedded or trigger parser vulnerabilities. Huge dimensions, duration, metadata, or decoder work can exhaust memory or CPU. | Allow only the documented static raster and audio formats plus bounded text; reject SVG, HTML, GIF, video, and unknown types. Check content signature as well as declared type/extension, never inline active markup, and set practical decode/render limits. Object URLs, if used, are limited to validated media and revoked when no longer needed. Owner: 21A and 22A. | Supply renamed SVG/HTML, polyglot files, unsupported formats, malformed PNG/WAV, extreme image dimensions, and excessive audio metadata. Confirm reject/diagnostic or bounded decode, no script or network, and no leak after closing or changing the view. |
| **P1: Player-save archive and JSON** (player-controlled save ZIP) | A forged or malformed save may exploit parser limits, inject state, mismatch content, or replace a valid live session before full validation. Save JSON must never become executable code. | Require the single documented save.json member and bounded ZIP/JSON parsing. Validate structure, references, ranges, and compatibility fields including project, game, engine, and playable-content fingerprint. Validate the entire payload before atomically replacing the live session; failure leaves it unchanged. Import never executes code. A slot limit cannot prevent copied files. Owner: 27A/27B and engine session owner. | Test traversal/duplicate members, malformed JSON, oversized/deep payload, unknown fields, invalid state and RNG values, and each compatibility mismatch. Confirm a clear rejection, unchanged session, and successful import of an unchanged valid save. Copying a save file should remain possible and is not a security failure. |
| **P1: IndexedDB recovery** (local project state and imported identifiers) | A malicious project may collide with another project's recovery key, poison a future restore, or repeatedly consume storage quota. A same-origin rendering bug could expose recovery data to project content. | Store project recovery as data and validate before restore. Use an application-owned record layout that prevents an imported project ID alone from overwriting another project’s recovery, and avoid destructive replacement until a valid snapshot is ready. Do not render stored strings as HTML. Surface quota failures while keeping in-memory edits recoverable; never report a failed write as success. Script and Markdown content receive no storage API. Owner: 11A/11B, 20A, and 19A. | Import projects with duplicate or crafted IDs, malformed recovery payloads, and a near-quota project. Confirm one project cannot silently replace another, failed writes show a diagnostic and retain current work, and reload restores only a validated snapshot. Attempt storage access from each script source. |
| **P0: Export serialization and generated HTML** (all playable data and compiled IR) | Authored strings such as a closing script tag, HTML entities, quotes, or Unicode separators may break out of a serialized-data context and execute code. Unsafe templating or HTML sinks can create stored XSS in every exported copy. | Serialize for the exact HTML/JavaScript context with safe escaping and a single well-defined parse path. Include a fixed trusted runtime and validated IR only. Render game text through safe nodes/text. Export declared playable files only. Review generated output, not only source templates. Owner: 28A/28B and 22B. | Export titles, node text, locale entries, CSS metadata, IDs, and script constants containing closing script tags, quotes, ampersands, U+2028/U+2029, and HTML payloads. Open extracted output from file in all supported engines. Confirm content is inert text/data, the story works, no new script is introduced, and no console exception occurs. |
| **P0: Direct-open resource boundary** (export and authored references) | A script, Markdown image/link, CSS rule, or malformed asset reference may contact the network, read unrelated local files, or depend on a server/module/fetch path that fails under file URLs. | Bundle trusted classic runtime and required data; use only validated relative managed assets for local media. No CDN, network fetch, module import, arbitrary local path, or authored automatic resource load. A CSP or browser sandbox may add defense in depth but is not proof by itself. Confirm behavior in each target engine and inspect requests. Owner: 1A, 19A, 28A/28B. | Open a clean extraction with networking disabled in Chromium, Firefox, and WebKit. Exercise scripts, links, CSS, images/audio, and save download/import. Record every request with full URL and status. Expected requests are the main document and explicitly declared local runtime, media, or style assets contained in the extraction; no HTTP(S), file paths outside the extraction, failed application requests, or reliance on a local server. Preserve the current WebKit/Safari evidence gap until closed. |
| **P2: External navigation and misleading content** (authored https/mailto links) | A story can socially engineer a player to visit a hostile site or send email. A new window can retain an opener and manipulate the game page. This is user-mediated phishing, not a sandbox escape. | Show the destination and require an explicit user click; never auto-open. If opening a new browsing context, sever opener access. Do not claim external destinations are safe or validate their content. Owner: 20A and 22A. | Confirm no link opens on render or keyboard focus. Activate an https and mailto link deliberately. If a new tab is used, verify it has no opener reference and the original game remains usable. |
| **P2: Dependency and browser variance** (ZIP, parser, sanitizer, runtime dependencies) | A compromised, vulnerable, or behaviorally inconsistent dependency may bypass validation in one browser or produce unsafe output. | Pin dependencies and review security updates through the integration owner. Keep security-sensitive parsing centralized behind owned APIs. Run the same hostile corpus across supported browsers; review dependency changes instead of silently updating during feature work. Owner: 1B dependency contract and 29A integration. | Re-run ZIP, script, Markdown, CSS, and export adversarial cases after dependency or browser updates. Record package/browser versions and compare accept/reject results. A dependency audit alone is not evidence that hostile input is safely handled. |

## Release verification checklist

A task owner should attach concrete evidence for its own row before the orchestrator accepts that security-sensitive path:

- [ ] ZIP import enforces actual byte, count, path, CRC, and time budgets before snapshot activation.
- [ ] Arbitrary files survive project import/export byte-for-byte and remain inert.
- [ ] Every script frontend rejects unsupported grammar. The executor accepts validated IR only, denies ambient capabilities, and rolls back budget failures.
- [ ] Markdown preview and player consume safe AST output; unsafe content cannot reach an HTML execution sink.
- [ ] Player CSS cannot affect editor chrome or cause resource requests.
- [ ] Media handling rejects active/unsupported formats and bounds decoding work.
- [ ] Save import validates the whole payload and compatibility before session replacement.
- [ ] Recovery quota and malformed-record failures are visible and preserve current in-memory work.
- [ ] Export serialization has adversarial string coverage and emits only declared playable inputs plus trusted runtime.
- [ ] Direct-open request traces are captured for Chromium, Firefox, and WebKit. The outstanding Task 1A evidence is resolved or reported as an explicit release blocker; no sandbox guarantee is inferred from a CSP message alone.

## Contract alignment and unresolved decisions

The security controls above follow the current product contract: hostile projects remain recoverable; unrelated files stay opaque; scripts compile to a capability-limited IR; state changes flow through engine validation; Markdown raw HTML is disabled; saves are explicit data-only ZIPs; and direct-open exports require no server or network. Numeric limits and some format details are cited from the in-progress 1B drafts and must be treated as draft values until Task 1B is accepted.

Task 1A remains unaccepted in the current docs. In particular, Chromium and Firefox spike results do not establish WebKit support, and the Safari screenshots do not demonstrate the full flow. Task 19A and 28B must retain this limitation until the required browser evidence is complete. This document introduces no production API, schema, new dependency, or product-contract change.
