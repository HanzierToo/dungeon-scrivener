# Shared data model and execution ordering

## Identifiers and values

Stable IDs are ASCII lowercase kebab-case, 1-64 characters, starting with a letter. IDs are references, not names. Display text may change without changing an ID. Script local names use ASCII identifiers and are a separate namespace.

A locale tag uses the syntax in the common schema and is resolved by exact tag, then the project's default locale. Missing keys produce a diagnostic and visible key fallback. No source text is rewritten.

A scalar is a string, finite number, or boolean. Integer-typed values must be safe integers. Enum values are strings from the declared set. Validation uses exact types with no coercion. State comparisons require both operands to have the same declared value type; ordering operators apply only to numbers. Equality and inequality apply to scalar values.

## Project and world documents

`project.json` is the project identity and default-locale manifest. Its required `gameVersion` is the one authoritative author-controlled game compatibility version. `world.json` is the game model. Both are independent schema-versioned documents. The world has one `entryNodeId`, node containment through `parentId`, and player navigation through separate `navigationEdges`. A node with `parentId: null` is a containment root. Containment cycles, duplicate IDs, unresolved references, and a nonvisitable entry node are semantic errors.

A node's `parentId` organizes it. It does not make the parent navigable. `visitable: false` marks an organizational node. Navigation only follows an authored navigation edge or an explicit `navigate` effect naming that edge.

`TextSource` is either literal text or a locale key. Locale lookup never changes the stored source. Raw text is valid even when no locale key is used.

## State, entities, events, and effects

State is scoped to the world, one node, or one entity. `StateReference` always names both a scope and a key. `world.stateDefinitions` declares typed world and node state keys; `EntityDefinition.fields` declares typed state keys for entities of that definition. `worldState`, `NodeDefinition.state`, and `EntityInstance.state` provide initial values; omitted declared keys use their definition default. Extra or mistyped values are semantic errors. Entity tags are separate from state. `EntityInstance.tags` are authored initial tags; the session's `entityTags` map is the mutable runtime set copied from those initial tags at session creation. `add-tag` and `remove-tag` update that set idempotently. Conditions and `api.hasTag` read the mutable session set. It is included in player-save snapshots so tag changes survive save/import.

Conditions are pure reads. `all`, `any`, and `not` compose conditions; `compare-state` reads a declared state key; `has-tag`, `at-node`, `event-is`, and `time-at-least` inspect the current snapshot or triggering event. Conditions do not mutate state.

Effects are requests handled by the engine reducer. `set-state`, `increment-state`, tag changes, event emission, navigation, inventory changes, conversation control, and `run-script` are the complete v1 effect union. The reducer validates every target and value before commit. A failed action rolls back all state changes and requested effects from that action. No UI or script mutates session state directly. Each transition returns ordered trace records; each record carries a sequence, source, and reason, and state-change records identify their state target and before/after values.

## Script invocation and action transactions

`run-script` names one declared script and is allowed in choice, command, dialogue-option, lifecycle, and rule effect lists. Invoking it calls that script's zero-argument `main` entrypoint. The engine executes effects in authored order. At a `run-script` effect, the script runs synchronously; its accepted `api.request` and `api.emit` calls are validated and applied to the action's provisional transaction in source execution order before the next authored effect. Events are appended to the FIFO event queue and rules consume them by the normal priority/order contract. Later effects and rules can read earlier script effects in the same transaction.

A script cannot request another `run-script` effect. After the current authored effect list finishes, the engine drains emitted events FIFO. For each occurrence, matching rules execute by descending priority and then authored array order; each triggered rule completes its ordered effects before the next matching rule begins. Events from a script or rule append to the same queue tail. Therefore an emit call queues an event but does not interrupt the remainder of the current script or effect list; later reads still observe all earlier provisional state/effect requests. Rule/event cascades may invoke more scripts, but every activation shares the action-wide activation and instruction budgets in `budgets.md`. Compilation or execution errors, invalid capability requests, and any budget breach return diagnostics, preserve an error trace, and discard the entire action transaction. The returned snapshot is value-equivalent to the input snapshot, including clock, RNG state, tags, inventory, and rule guards. Random entropy consumed by a failed action is not committed; a subsequent retry may draw a different unseeded value.

An event definition declares its payload fields and types. Each occurrence carries one event ID, JSON payload, and source reason. Event payload validation checks required declared fields and rejects unknown or mistyped fields. The event queue is FIFO. Rule effects that emit events append occurrences to its tail.

A rule listens to one event ID or one lifecycle phase. Eligible rules run by descending priority, with equal-priority rules in authored array order. Inherited rules run parent before child; each node retains its own array order. A rule condition is evaluated against the snapshot and triggering event for that rule activation. Cascades stop at the limits in `budgets.md`; a limit failure rolls back the enclosing action.

## Nodes and actions

The node hierarchy is independent of navigation. `inheritance.defaults` and `inheritance.rules` opt into inheritance from the parent chain. If either flag is omitted, it is false. World-level `actionDefaults` are the baseline. For each action category independently, inherited parent configuration is applied first, then the node's present category replaces that category. An empty array explicitly disables a category. Choices and typed commands may both be available.

Choice and command conditions determine whether the action is available. A false condition hides the action by default; `falsePolicy: "disable"` keeps it visible and disabled. Commands carry an ordered `patterns` array: the first is canonical and following patterns are aliases. Each placeholder such as `{target}` must name one declared parameter and occupies one whole input token. A command may also carry a navigation edge and ordered effects.

Command matching normalizes both authored patterns and user input to Unicode NFC, trims leading and trailing Unicode White_Space, collapses each internal run of Unicode White_Space to one ASCII space, and applies locale-independent lowercase before literal comparison. Token boundaries are the normalized ASCII spaces. Matching requires the same token count. A placeholder captures exactly one token; quoted phrases and multi-token captures are not supported. String captures preserve their normalized spelling. Number captures use JSON decimal syntax `-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?` and must be finite. Integer captures must also be safe integers. Boolean captures are `true` or `false`, case-insensitively. Enum captures compare case-insensitively to a declared value and return its declared spelling. A capture that fails conversion does not match. The public player route accepts `PlayerInput`: a choice ID or raw command text. Raw command text passes through `matchCommandText` and then `dispatchPlayerInput`; callers do not construct typed parameter maps themselves. The matcher considers commands available at the current node after inheritance; commands hidden by a false condition are excluded, while disabled commands remain candidates so dispatch can return a disabled resolution. If no command matches, resolution is no-match. If different command IDs match, resolution is ambiguous and includes unique IDs sorted by code-point order, independent of authored order, alias order, or locale. No-match and ambiguous inputs preserve the snapshot and do not consume action time. A uniquely matched but disabled command is resolved as disabled and also preserves the snapshot. A uniquely matched enabled command dispatches its converted captures as one action.

The exact byte, scalar, token, command, pattern, parameter, and token-comparison bounds are in `budgets.md`. Malformed UTF-16, an over-limit raw string, or an over-limit effective command set returns `invalid-input` with a diagnostic; it is not a no-match and is never truncated. `dispatchPlayerInput` returns the original snapshot and consumes no action time for invalid input.

The `patterns` array order only identifies the canonical pattern; it does not give matching precedence over another command. Repeated patterns after normalization within one command, placeholders that are missing/unused/duplicated, type-invalid patterns, and duplicate command IDs are semantic validation errors. Different command IDs may overlap; raw input matching more than one command returns ambiguous with unique command IDs sorted by code-point order and applies no action.

## Lifecycle and time

Entry, revisit, and exit lifecycle effects use one of `every-time`, `first-time`, or `once-per-playthrough`. `first-time` runs on the first visit. `once-per-playthrough` runs only once in the session even if the node is revisited. Rule guards and visit counts are session state and are included in player saves.

Per-action time adds the positive `millisecondsPerAction` after each accepted action, including script and rule cascades as part of that action. Rejected, ambiguous, disabled, or rolled-back actions do not add per-action time. Elapsed time advances only through host calls to `observeClock`; the engine never reads browser globals. `ClockInput` carries `tick`, `visibility-change`, `focus-change`, or `resume`, an epoch-millisecond timestamp, current visible/hidden state, and focus state. The host sends ticks while active and a new observation on visibility/focus changes and when a suspended page resumes. Either hidden or unfocused means inactive.

For elapsed worlds, a new session stores the host's current timestamp and activity state. Each accepted observation updates `clockState` with visibility, focus, last observed epoch milliseconds, and the start of the current inactive interval. While previously active, elapsed time between observations is added. On a pause-policy transition or resume after suspension, the inactive interval adds zero. On a bounded-catch-up transition or resume, the inactive interval adds the lesser of its duration and `maxCatchUpMilliseconds`. A resume is always treated as an inactive interval from the last baseline, even if the last saved activity flags were active, because the page may have been closed without a final event. The new baseline is the resume timestamp; time before it cannot be awarded again after save/load. Timestamps are safe integers from zero through `Number.MAX_SAFE_INTEGER`; a timestamp earlier than the stored baseline is rejected with a clock diagnostic and leaves both time and baseline unchanged. Repeated timestamps are valid no-op observations. Inputs are never coerced or clamped. For per-action worlds, clock inputs do not advance time and both epoch baselines remain null. The save persists visibility, focus, last observation, and inactive-start baseline so pause and bounded-catch-up apply consistently across suspension and save/load. `showClockHud` controls whether a clock projection is included in `PlayerView`. See `budgets.md` for exact limits.

## Randomness and typing sounds

The author selects `world.settings.randomness.mode`. A seeded session uses the optional `SessionStartOptions.randomSeed` when supplied; otherwise the engine requests one uint32 value from `GameEngineHost.seededSeedSource`. A supplied seed is validated as uint32 and the host source is not called. If neither a valid supplied seed nor a valid host value is available, session creation fails; the engine never substitutes time, a constant, or an unseeded draw. Normalize seed zero to `0x6d2b79f5`. The engine uses xorshift32: for every raw draw apply `x ^= x << 13`, `x ^= x >>> 17`, `x ^= x << 5`, and store the result as uint32. `randomInitialSeed` stores the normalized session-start seed, and `randomSeed` stores the current state. Both are saved, so a save can identify the session seed and continue the same future sequence. A random float is the raw uint32 divided by `2^32`. For inclusive integer bounds `minimum` and `maximum`, let `range = maximum - minimum + 1` and `limit = 2^32 - (2^32 mod range)`; draw until the uint32 is less than `limit`, then return `minimum + (draw mod range)`. The range must be between 1 and `2^32`; more than 64 raw draws for one request is a runtime diagnostic. Seeded calls update PRNG state only when the enclosing action commits.

Unseeded sessions need no entropy source until a random call occurs; each such call requires `GameEngineHost.unseededRandomSource`, whose `nextUint32()` returns uniformly distributed uint32 values, unless `unseededRandomReplaySource` is supplied. If neither source is available when a call occurs, the action fails with a randomness diagnostic. A replay source takes precedence over entropy and returns the recorded `UnseededRandomOutcome` for each exact `RandomOutcomeRequest` (ordinal, source script, operation, and bounds); an exhausted, mismatched, or out-of-range record fails the action and never falls back to fresh entropy. A replay harness must also verify that the complete expected action transcript consumed the complete supplied log, so extra records are reported as replay mismatch. They have `randomInitialSeed: null` and `randomSeed: null`; an optional seed supplied at session start is an error. Every accepted draw is appended to the ordered `randomOutcomes` log with ordinal, source script, operation, bounds, and returned value. Failed atomic actions do not commit outcomes. The fixed history limit is in `budgets.md`; reaching it causes a random request and its containing action to fail rather than truncate history. No global random API is available to scripts. Changing the seeded algorithm is a breaking engine behavior and requires an engine-version change.

## Compiled scripts and executor boundary

The engine receives a `CompiledScriptBundle` and synchronous `ScriptExecutorApi` at construction. At a `run-script` effect, it calls `executeScript(ir, context)` inline, at that effect's position. The context has the current caller origin, remaining instruction limits, and capability callbacks. Reads observe the transaction's provisional state. `request` validates and applies a script effect immediately to that provisional state; `emit` queues the event for the existing FIFO drain after the current effect list. Neither executor nor script gets a mutable snapshot. A successful return reports instructions and sparse source-spanned activation/capability trace; a failed return carries one diagnostic and the same trace. The engine incorporates script trace records into the action trace, checks reported counts, and rolls the entire action back on script error, unexpected executor exception, invalid capability request, or budget breach. Exact limits are in `budgets.md`.

The bundle may be empty. `createSession(projectId, world, options)` checks that it contains exactly one IR per declared `world.scripts` entry, matched by ID, path, language, and entrypoint. This check is deferred to session creation because the factory has no world argument. Session creation returns `{ ok: true, snapshot }` or `{ ok: false, diagnostics }`. Invalid supplied seeds, unavailable or invalid host seed values, unsafe start-clock values, and bundle mismatch produce the failure form; there is no partial snapshot. Script-capable operations validate the supplied world against the engine's stored bundle again before processing. If a later supplied world changes its script declaration set incompatibly, the transition returns the original snapshot and diagnostics. A world with the same script declarations is compatible for this check.

Typing sounds are local managed WAV assets. A mapping targets one case-sensitive standardized `KeyboardEvent.code` or one key group; its asset hash and volume in the inclusive range 0-1 are required. The letters group is `KeyA` through `KeyZ`; digits are `Digit0` through `Digit9` and `Numpad0` through `Numpad9`; space is `Space`; punctuation is the standardized punctuation codes `Backquote`, `Backslash`, `BracketLeft`, `BracketRight`, `Comma`, `Equal`, `IntlBackslash`, `IntlRo`, `IntlYen`, `Minus`, `Period`, `Quote`, `Semicolon`, and `Slash`; editing includes Backspace, Delete, Enter, Tab, Escape, arrows, Home, End, PageUp, PageDown, and Insert; other is every remaining code. An exact-key mapping takes precedence over its group mapping. Duplicate targets are semantic errors. Volume is a linear gain where 0 mutes and 1 applies no extra attenuation; out-of-range values are schema/semantic errors and are never clamped. `PlayerView.typingSounds` is always present; absent world configuration becomes an empty mapping list with silent fallback. Otherwise it carries each mapping's resolved asset ID/media type/byte length, volume, and fallback. The player obtains bytes only by calling `MediaAssetApi.resolveAsset(assetId)`, which verifies the content hash and returns the bytes without exposing a VFS path. The media validator accepts only a well-formed RIFF/WAVE file with one supported `fmt ` chunk and one `data` chunk, consistent sizes/alignment, PCM or IEEE-float encoding, 1-2 channels, 8-192 kHz, PCM 8/16/24/32-bit or float32. Missing, hash-mismatched, or malformed referenced files block play/export with a diagnostic. If an asset becomes unavailable or the browser cannot decode/play it, the player uses the configured fallback; if that fallback also fails, it stays silent and reports a media diagnostic. No network request is made.

## Player view and diagnostics

`PlayerView` is a read-only snapshot projection. It contains resolved locale strings, safe Markdown AST, available choices and commands, optional dialogue/inventory/clock sections, required typing-sound configuration, and compact diagnostic summaries. Typing-sound references are content-addressed metadata; `MediaAssetApi.resolveAsset(assetId)` supplies verified bytes to the player. The safe AST never contains trusted raw HTML.

Diagnostic codes are stable identifiers in the form `DS-<AREA>-<NUMBER>`. `blocks` names behavior that cannot proceed. `acknowledgementRequired` separately names the user actions that require acknowledging a warning. A blocking action and an acknowledgment are distinct controls; severity alone does not imply either.
